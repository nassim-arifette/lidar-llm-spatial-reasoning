\begin{abstract}
\noindent
LiDAR-LLM \cite{lidarllm} couples a frozen LiDAR encoder to a large language
model so that spatial questions about a driving scene can be answered in
natural language. Our original project reimplemented a reduced version of that
architecture and showed, honestly, that it could not be trained on the
hardware available. This report changes the question rather than the hardware.
Holding perception fixed, we ask whether a spatial question about a LiDAR
scene is better answered by \emph{producing} the answer or by \emph{computing}
it, and we ask it of one model so that the two are genuinely comparable: the
same frozen Qwen2.5-1.5B-Instruct either answers from the object list, or
writes a small program that a deterministic executor runs on that same list.
On $200$ held-out questions from three unseen nuScenes drives the executed
mode reaches $0.685$ against $0.505$; paired question by question it is alone
correct on $67$ and alone wrong on $31$ ($p = 3.5\times10^{-4}$), and its
counting error is $0.68$ against $2.16$ at equal numeric coverage. The sharper
instrument is a scene-dependence control: of thirteen questions asked verbatim
of two scenes with different answers, the executed mode is right on all
thirteen and the direct mode on one. Two findings about the data matter beyond
this comparison. The six nuScenes-QA relations are recovered empirically from
box geometry --- uniform $60^{\circ}$ bearing sectors fit the reference
answers better than five alternatives including the six camera frusta --- and
$23\%$ of nuScenes annotations carry \emph{zero} LiDAR returns while
nuScenes-QA counts them anyway, so filtering objects by LiDAR support, the
obvious thing to do, costs $49$ accuracy points. Nothing here is trained, and
the whole study runs on one free T4.
\end{abstract}

% =====================================================================
\section{Introduction}
% =====================================================================

Interpreting a LiDAR scene in natural language is attractive for autonomous
driving: a system that can answer ``how many cars are ahead of us?'' exposes
its scene understanding in a form a human can audit. LiDAR-LLM
\cite{lidarllm} pursues this by aligning a LiDAR representation with the
embedding space of a language model through a three-stage curriculum, with
GPT-4 \cite{gpt4} improving the captions that form the training data and
LLaMA-7B as the model that learns from LiDAR.

Our first report reimplemented a reduced version of this architecture.
Section~\ref{sec:original} restates what that implementation did and, more
usefully, what it failed to establish. Section~\ref{sec:question} argues for a
different question, one the same hardware can answer.

The shift is motivated by an observation about counting and directional
questions. When the correct answer to ``how many cars are in front?'' is
determined by the object list and a geometric predicate, asking a generative
model to emit the digit is asking it to re-derive, inside its weights, a
computation that is already exact and essentially free. Whether that
re-derivation buys anything is testable, and this report tests it on one model
used two ways.

% =====================================================================
\section{The original re-implementation and what it did not show}
\label{sec:original}
% =====================================================================

The first version implemented the LiDAR-LLM pipeline in reduced form: a small
PointNet encoder, a view-aware transformer with six view-position embeddings,
an MLP adapter projecting into the token embedding space, and GPT-2
\cite{gpt2} fine-tuned with LoRA \cite{lora}. Data came from nuScenes-mini
\cite{nuscenes} with nuScenes-QA \cite{nuscenesqa} questions: 323 training
samples from 8 scenes, 81 validation samples from 2 scenes.

It produced a debugged pipeline and no evidence. Training ran on laptops with
roughly 6\,GB of RAM and no GPU. The functional check was that the model could
be driven to emit a fixed string regardless of the LiDAR input, which shows
that gradients flow and nothing more.

Three weaknesses shape what follows.

\paragraph{The evaluation could not separate competence from priors.}
nuScenes-QA answers are skewed towards ``no'' and small integers. With no
question-only control, an accuracy figure cannot distinguish a model that reads
the scene from one that has learned the answer distribution. Real-3DQA
\cite{real3dqa} shows how severe this is: on SQA3D a model fine-tuned on
question--answer pairs \emph{with no 3D input at all} matches or beats existing
3D-LLMs, and filtering the blind-answerable questions collapses LEO's exact
match from $49.4\%$ to $14.3\%$.

\paragraph{The split invited leakage.} Splitting questions rather than scenes
puts different questions about the same LiDAR sample on both sides, rewarding
``this scene has three cars''.

\paragraph{The target task did not need a language model.} Counting, existence
and directional questions have answers that are functions of the object list.

% =====================================================================
\section{A question the available hardware can answer}
\label{sec:question}
% =====================================================================

We fix perception and vary only the reasoning stage. Every system receives
exactly the same object list, and the question becomes:

\begin{quote}
\emph{At a fixed language model and fixed scene data, is it more reliable to
produce the answer to a spatial question, or to produce an executable program
and let a deterministic executor compute the answer?}
\end{quote}

Posed between \emph{two uses of one model}, this is answerable without
confounds. A learned answer head and a program-writing model differ in
architecture, in training and in what they see, so a gap between them says
little; the same checkpoint, the same decoding and the same objects differ in
exactly one respect.

\paragraph{Relation to existing work.} The idea is not ours. CLEVR
\cite{clevr} established the template: represent a question as a functional
program over a small catalogue of operations --- filter, unique, relate,
count, exist, query, compare --- and execute it on the scene graph.
Neural-symbolic VQA \cite{nsvqa} then showed that recovering such a program
and executing it on a structured scene representation is far more accurate on
CLEVR than predicting the answer end to end. Our qualitative result is a
reproduction of that finding on real driving data with a frozen $1.5$B model
and no training at all; the contribution is the controlled measurement and the
two data findings of Section~\ref{sec:method}, not the idea.

Closer in domain, ZSVG3D \cite{zsvg3d} produces programs from language for
zero-shot 3D grounding. KLDrive \cite{kldrive} merges multi-source evidence
into a scene knowledge graph and lets a frozen Qwen3-7B agent reason over it
through a Plan--Execute--Observe loop, reaching $65.04\%$ overall and $64.46\%$
on counting against $18.45\%$ for its strongest baseline. Retrieve-to-Localize
\cite{retrieve2localize} makes the complementary argument for coordinates.
BEV-LLM \cite{bevllm} extends LiDAR-LLM with camera images through BEVFusion.
NuScenes-SpatialQA \cite{nuscenesspatialqa} finds a spatially enhanced VLM
improving on qualitative questions while remaining uncompetitive on
quantitative ones --- precisely the counting gap targeted here. 3DGraphLLM
\cite{3dgraphllm} learns a scene-graph representation carrying semantic
relations.

Two things prevent a direct numerical comparison. These systems change more
than the reasoning module --- KLDrive's accuracy is obtained with three
detectors over $39{,}704$ selected questions under a random $8{:}2$ split that
is not stratified by scene, so part of the gain is perception and part is
protocol. And ``frozen LLM'' does not mean cheap: KLDrive runs on RTX A6000s,
Retrieve-to-Localize trains on four A6000s, BEV-LLM's 1B variant takes 48
hours on eight A100s. The experiment below runs in under three minutes on one
free T4.

\section{Method}
\label{sec:method}
% =====================================================================

\subsection{Object-level scene representation}

A scene is a list of objects, each with a canonical class (the ten nuScenes
detection classes), a centre, a box size, a yaw, a detection score and, where
the annotation carries one, a \emph{status} --- moving, parked, stopped,
standing, sitting/lying down, with rider, without rider. All coordinates are
in the ego frame: $x$ forward, $y$ left, $z$ up. nuScenes boxes and released
detection results are in global coordinates, so the conversion through the
sample's ego pose and the quaternion-to-yaw step are performed explicitly and
in one place; a sign error there mirrors the scene and would be
indistinguishable from a reasoning failure.

An unknown status is treated as neither the attribute nor its negation. A
traffic cone carries no attribute, so it is not ``standing'' and not ``not
standing''; counting it under the negation would assert something the
annotation does not support.

\subsection{Directions as bearing sectors, recovered rather than assumed}
\label{sec:sectors}

nuScenes-QA uses six spatial relations. Our first implementation used eight
$45^{\circ}$ octants, which silently answered a different question: an object
at a bearing of $50^{\circ}$ is ``front left'' under one convention and
``left'' under the other, and ``left'' does not exist in the six-relation
vocabulary at all.

Rather than replace one assumption with another, the convention was
\emph{measured} against the benchmark's own answers. Over the $68$
ego-anchored directional questions of the evaluation manifest we scored five
candidate definitions by exact agreement with the reference answer:

\begin{table}[h]
\centering
\small
\begin{tabular}{lrrr}
\toprule
Candidate convention & Exact & Count MAE & Bias \\
\midrule
\textbf{Uniform $60^{\circ}$ sectors, $y$ left, no range limit}
                                   & \textbf{76.5\%} & 1.24 & $-1.14$ \\
Same, with $y$ pointing right      & 72.1\% & 0.76 & $-0.76$ \\
The six nuScenes camera frusta     & 67.6\% & 1.76 & $-0.62$ \\
Eight $45^{\circ}$ octants         & 61.8\% & 1.62 & $-1.62$ \\
Overlapping quadrants ($x>0$, $y>0$, \ldots) & 51.5\% & 3.86 & $+2.62$ \\
\bottomrule
\end{tabular}
\caption{Recovering the relation definition from the gold answers. The camera
row uses the real calibration: each camera's optical axis and horizontal field
of view are computed from \code{calibrated\_sensor.json} and the intrinsics,
and an object belongs to a camera if it projects inside that image.}
\label{tab:sectors}
\end{table}

The six-camera hypothesis is tempting --- six relations, six cameras, named
\code{CAM\_FRONT\_LEFT} and so on --- and it is wrong: the frusta overlap and
are unequal in width ($64$--$89^{\circ}$ from the intrinsics), and they fit
worse than uniform sectors. Every maximum-range cut from $25$ to $60$\,m also
makes the fit worse, so nuScenes-QA counts objects at any distance.

The residual is structured: on the development split the executor agrees with
$50/50$ non-directional questions, $17/18$ axial ones (front, back) and
$24/32$ diagonal ones, with \emph{front left} alone at $5/10$. The boundaries
were deliberately \emph{not} fitted to close that gap. An executor whose
sector edges were tuned on the reference answers would help the branch that
computes with those edges far more than the branch that only reads them in
prose, and the comparison of Section~\ref{sec:results} would be measuring the
tuning.

Objects closer than $1$\,m to the ego origin are excluded from directional
queries, because a $10$\,cm localisation error flips the sign of their
bearing. Relative directions (``left of the truck'') are ambiguous between the
viewer's frame and the object's own frame; both are implemented, and the
viewer-centric reading is the default, matching nuScenes-QA.

\subsection{What the LiDAR returns say about the labels}
\label{sec:lidar}

nuScenes annotates every object a human could see, and records how many LiDAR
points fall inside each box. Building a scene from LiDAR, the natural move is
to keep only annotations the sensor actually hit. On the mini split that
discards \textbf{$4{,}278$ of $18{,}538$ annotations --- $23\%$ --- for having
zero LiDAR returns}.

It is also wrong for this benchmark. Holding the programs fixed and changing
only the object list, over the $125$ counting questions that both conditions
answer numerically:

\begin{table}[h]
\centering
\small
\begin{tabular}{lrrr}
\toprule
Object list & Accuracy & Under-counting & MAE \\
\midrule
Keep only annotations with $\geq 1$ LiDAR return & 0.336 & 1.672 & 1.76 \\
\textbf{Keep every annotation}                   & \textbf{0.824} & \textbf{0.568} & \textbf{0.69} \\
\bottomrule
\end{tabular}
\caption{Same questions, same programs, same geometry; only the object list
changes. Filtering by LiDAR support costs $49$ accuracy points.}
\label{tab:lidar}
\end{table}

So nuScenes-QA's reference answers count objects the LiDAR never saw. This is
a fact about the benchmark rather than about reasoning, and it is worth stating
plainly because the filter is the obvious engineering choice and it is
expensive. Every experiment below therefore uses the unfiltered list, and the
choice is recorded in the manifest so both compared systems inherit it.

\subsection{From question to program}

A program is an operation (\textsc{count}, \textsc{exists},
\textsc{compare}) over a selector: a category or category group, an optional
status, an optional region (a bearing sector, near, far, or a radius), and an
optional anchor making the region relative to another object. Two parsers emit
this language. A deterministic rule grammar serves as a reference and as a
baseline; the frozen language model is the system under test.

The grammar declines what it cannot represent rather than guessing. This
matters more than it sounds: an earlier version had no slot for a status word
and silently dropped it, so ``what number of stopped things are there'' was
executed as ``how many objects are there'' and answered $71$ against a
reference of $10$. Making the grammar able to carry the attribute and the
preamble referent raised its end-to-end accuracy on all $5{,}916$ mini
questions from $0.156$ (drop what you cannot express) to $0.231$ at the same
coverage, with accuracy-when-answering rising from $0.632$ to $0.856$.

\subsection{Execution}

Executing a program is a filter followed by an arithmetic operation. It is
deterministic, has no learned parameters, and returns the objects it selected,
which is what allows an error to be attributed to perception rather than to
reasoning. A definite reference whose resolution is ambiguous (``the truck'',
when the scene has three) is refused rather than resolved by taking the first
match. CLEVR avoids such questions at generation time, calling them ill-posed
\cite{clevr}; on data we did not generate, well-posedness has to be detected
instead, and a refusal is counted as a wrong answer throughout.

\section{Experimental protocol}
% =====================================================================

\subsection{The frozen example set}

Both systems are measured on one set, fixed before either ran
(\code{manifests/first\_comparison.json}): $100$ development and $200$
evaluation questions drawn from nuScenes-QA mini, over nuScenes ground-truth
annotations.

\paragraph{Split by scene, never by sample.} Consecutive samples of one drive
show the same vehicles, so splitting by sample would make the evaluation set a
paraphrase of the development set. Development holds seven drives, evaluation
three, with no overlap.

\paragraph{Selection by what the question asks, not by what a parser manages.}
Families are assigned from the question's surface structure --- does it name an
attribute, a direction, a reference object --- using the lexicons directly.
Keeping the questions the grammar happens to parse would quietly select the
examples that favour the executed branch. Of the $5{,}916$ mini questions
$1{,}626$ are in scope; the $4{,}290$ excluded are recorded with their reason
($2{,}199$ belong to a template outside this scope, $1{,}005$ bind an
attribute to another object, $86$ name no known class).

\paragraph{What fixes the scope, precisely.} It is the \emph{rule grammar},
not the flat language. The flat language has operations for identifying an
object, querying its attribute and comparing two objects' attributes, so it
could attempt the \code{object}, \code{status} and \code{comparison}
templates. The rule grammar cannot, and the rule grammar is what produces the
reference programs that let the executor be checked before any model runs
(Section~\ref{sec:verify}). Restricting the first comparison to what can be
independently verified is the reason; it is a smaller claim than ``what the
language can express'', and Section~\ref{sec:wide} measures the difference.

\paragraph{Four families}, in increasing structural demand: category only
(``are there any cars''), category with an attribute (``how many parked
cars''), category in an ego-relative region, and category anchored on another
object (``behind the truck''). The reference answer is available to the
evaluator and not to either inference function.

\paragraph{An oracle perception condition.} Object lists are ground-truth
annotations, not detections. This is deliberate: it fixes perception so the
comparison is about what each system does with a scene rather than who sees it
better. It also bounds the claim --- nothing in Section~\ref{sec:results}
speaks to detection quality.

\subsection{The executor, checked before any model ran}
\label{sec:verify}

Attributing a wrong answer to the model requires knowing the executor is
right. On the development split, reference programs produced by the rule
grammar and read by hand were executed on the frozen object lists with no
model involved: \textbf{$91/100$}, with the category-only and attribute
families at $25/25$. All nine disagreements were read and categorised:
\emph{eight} are the diagonal-sector residual of Section~\ref{sec:sectors},
and \emph{one} is a question whose definite reference (``the not standing
pedestrian'') matches $22$ objects --- nuScenes-QA answers it anyway, so its
one-hop templates appear to read the reference existentially rather than as a
definite description. That disagreement is left as a refusal and charged
against the executed system, not excused.

\subsection{Matched conditions}

Both modes use the same checkpoint (Qwen2.5-1.5B-Instruct) loaded through one
shared runtime, the same dtype, greedy decoding, and the same $256$-token
budget. Both receive the same object rows at the same rounding, in an order
that does not depend on the question --- no list pre-filtered by what is being
asked, no precomputed counts. Both are told the same conventions: the ego
frame, the six sectors with their numeric bounds, and the treatment of unknown
status.

Two safeguards are worth naming. Prompts longer than the context budget are
\emph{refused} rather than trimmed, because trimming deletes objects and the
loss would be scored as a reasoning error; and every generation records
whether it stopped on its own or ran out of budget, after an earlier run lost
$26\%$ of its programs to a $96$-token budget, $97\%$ of them to truncation ---
a configuration choice that had been read as a model failure. In the runs
reported here no generation was truncated.

The caches are separate and keyed differently. A program depends on the
question; a direct answer depends on the question \emph{and} the scene.
Sharing a key would serve one scene's answer for another's, destroying the
control of Section~\ref{sec:scene}.

\paragraph{Only one family generalises cleanly.} The attribute family is a
large, consistent win ($+0.36$ then $+0.42$): applying ``parked'' as a filter
is exactly what an executor does and a $1.5$B model does not. The other three
move substantially between the splits --- the ego-relative gain falls from
$+0.48$ to $+0.02$, and the category-only comparison changes sign. At $25$ to
$54$ questions per family these are too noisy to carry an argument, and we do
not build one on them. Had only the development split been run, the
ego-relative row would have looked like the headline finding; it is the
clearest argument in this report for holding scenes back.

\paragraph{The direct model does not scan the list.} Its errors are not
marginal. Where the reference is $7$, $9$ or $10$ it answers $1$, $3$ and $2$;
on preamble questions it answers $1$ almost regardless of the scene. With
forty-odd object rows in the prompt, a $1.5$B model emits a small number rather
than enumerating. Its under-counting ($1.84$--$2.08$) dwarfs its over-counting
($0.31$--$0.35$), the signature of not looking rather than of looking badly.
Its answer \emph{format} was never the obstacle: all three hundred direct
outputs parsed.

\paragraph{Cost.} The two modes are closer than the accuracy gap suggests. On
evaluation A consumes $217{,}272$ input and $400$ output tokens, B $178{,}402$
input and $9{,}731$ output: B reads less, because it never sees the objects,
and writes twenty-four times more, because it writes a program. Wall-clock
generation is $59$\,s against $101$\,s on one T4, both batched identically.

internally, or simply because it cannot count rows in a forty-line table of
floats --- a weakness a larger model might not share. Repeating the comparison
at two more sizes, changing nothing else, separates them.

is $65$\,GB in bfloat16 and the card holds $40$; quantisation can only hurt
it, so that row understates the large model.}
\label{tab:size}
\end{table}

\paragraph{Scale does not rescue the direct mode.} It gains $0.075$ across a
twenty-one-fold increase in parameters, and $0$ of that between $1.5$B and
$7$B. The identical $0.505$ at the first two sizes is not a cached result: the
$7$B changes its answer on $89$ of the $200$ questions and flips correctness on
$52$ of them, $26$ in each direction. It answers differently and is wrong just
as often. Whatever the direct mode is failing at, it is not something $4.7$
times the parameters fixes.

\paragraph{What scale does fix is program validity.} Programs the executor
cannot parse fall from $8$ to $1$ to $0$, and the answered fraction rises from
$0.910$ to $0.995$. The executed mode gains $0.160$ from $1.5$B to $7$B and
then only $0.020$ more at $32$B: the remaining errors are no longer about
writing a well-formed program.

\paragraph{The gap widens before it stabilises} --- $+0.180$, $+0.320$,
$+0.265$ --- and the paired tables stay decisive at every size ($p =
3.5\times10^{-4}$, $1.2\times10^{-11}$, $1.1\times10^{-9}$). The honest
reading is not that language models cannot do this. It is that, over the range
we could afford to test, the capacity gained by scaling went into writing
better programs and almost none of it into answering from the table directly.

\subsection{The scene-dependence control}
\label{sec:scene}

Thirteen evaluation questions appear verbatim on two scenes with different
reference answers. A system that does not read the objects gives the same
answer to both and scores on whichever scene matches its prior.

\section{Where the executed system fails}
\label{sec:failures}
% =====================================================================

An accuracy of $0.685$ says nothing about what to do next. The $31.5\%$ that is
wrong contains four problems with four different remedies, and they are
separable without a model: where the model's program matches the deterministic
grammar's and the answer is still wrong, the program is not at fault.

\begin{table}[h]
\centering
\small
\begin{tabular}{lrrl}
\toprule
Failure & $n$ & share & what it asks for \\
\midrule
Program says something else   & 27 & 43\% & better prompt, examples, bigger model \\
\quad wrong operation         & 22 &      & \code{count} written for an existence question \\
\quad wrong or dropped status & 2  &      & \code{not with rider} for \code{without rider} \\
\quad other                   & 3  &      & \\
Program right, answer wrong   & 18 & 29\% & the executor and the data \\
Refused at execution          & 10 & 16\% & ambiguous (8) or missing (2) reference \\
Malformed output              & 8  & 13\% & a budget, or constrained decoding \\
\midrule
Total                         & 63 & 100\% & \\
\bottomrule
\end{tabular}
\caption{The executed system's $63$ evaluation failures, triaged.}
\label{tab:triage}
\end{table}

Three conclusions follow, and they decide where effort should go.

\paragraph{The bottleneck is writing the program, not executing it.} Forty-five
of $63$ failures ($71\%$) are the model producing a program that does not match
the question, or no program at all. Only $18$ ($29\%$) survive to the executor
and disagree there, and those are the diagonal-sector residual of
Section~\ref{sec:sectors}. Widening the target language --- the obvious next
engineering move, and one we deliberately did not make --- would address almost
none of this.

\paragraph{The largest single failure is a format mismatch, not a
misunderstanding.} In $22$ cases the model writes \code{count} for a question
asking \code{exists}: ``are there any moving cars to the front left of me?''
becomes a counting program. The selector is usually right; the answer is then
an integer, which can never match a yes/no reference. One third of all failures
is a model that understood the scene query and chose the wrong return type.

\paragraph{The malformed outputs have one cause.} All eight emit
\code{"category": "*"} for ``things'', a token outside the vocabulary, although
the prompt lists the ten classes \emph{and} states the rule mapping ``thing''
to \code{object}. The instructions are not at fault; a $1.5$B model is. This is
the clearest single thing to re-test with a larger model, and the one category
of failure that grammar-constrained decoding would eliminate by construction.

\section{A preliminary study on synthetic scenes}
\label{sec:synthetic}
% =====================================================================

Before the nuScenes protocol existed, the same executor was compared against
\emph{trained} baselines on a synthetic corpus, under the earlier
$45^{\circ}$ octant convention. Those numbers are reported here as a
preliminary study, not as results on nuScenes-QA, and the convention alone
makes them non-comparable with Section~\ref{sec:results}.

Scenes are sampled with nuScenes-like class frequencies, questions are
generated \emph{from} programs so every gold program is known, and a
detector-failure model (12\% drops, 5\% duplicates, $0.6$\,m jitter) produces
a ``detected'' list. \textbf{This simulates detector behaviour; it does not
measure a detector.} No 3D detector was run anywhere in this project, and no
claim about detection quality is made from it.

Neither learned model beats the question-only control. On contrast pairs the
gap is starker: a blind model must score zero, deep sets reaches $0.022$ and
the counter $0.076$, against $0.643$. On the accuracy column one could argue
the learned models use the scene a little; on contrast pairs they essentially
do not.

Two cautions that the nuScenes work later confirmed. First, benchmark design
changes the conclusion: on an unbalanced version of the same corpus, where
$75\%$ of answers mean ``nothing there'', the learned models appear to beat the
blind baseline while their contrast-pair accuracy stays near zero. Second,
these learned baselines were also run on real nuScenes-QA questions, where
deep sets does \emph{not} reliably beat the blind prior --- paired by seed the
margins are $-0.021$, $+0.032$, $+0.025$ --- and where replacing ground-truth
objects with simulated detections moves it by $+0.019$, $-0.030$, $+0.010$. A
model whose score is unchanged when the 3D input is corrupted has not been
shown to use it.

% =====================================================================
\section{Discussion}
% =====================================================================

\paragraph{What this establishes.} At a fixed language model, fixed scene data
and fixed conventions, emitting an executable program was substantially more
reliable than emitting the answer: $0.685$ against $0.505$ on held-out drives,
with a paired advantage of $67$ to $31$ and a counting error three times
smaller at equal coverage. The scene-dependence control separates the two
modes more sharply than any aggregate. The study is also cheap enough to
repeat: nothing is trained, and the whole comparison is three minutes on a free
T4.

\paragraph{What it does not establish.} Branch B brings hand-written code that
implements the benchmark's semantics, verified at $91/100$. Its ceiling is high
by construction, and the question is really whether the \emph{model} can write
the program --- which it does validly $92$--$96\%$ of the time, reaching
$0.753$ when it does. The result is not evidence that language models cannot
reason about space. The baseline is also weak in a specific way: a $1.5$B model
asked to count rows in a $44$-line table of floats is being tested on something
it is known to be poor at, and part of A's disadvantage may be context length
rather than reasoning. Objects are ground truth, so nothing here speaks to
perception. And the evaluation rests on three drives.

\paragraph{The one experiment that would settle the open question.} Repeating
the comparison with a substantially larger checkpoint, changing nothing else,
separates the two explanations currently confounded: ``the model cannot write
the program'' and ``the model cannot count from a table''. If the direct mode
catches up at scale, the result is a fact about model size; if it does not, it
is a fact about the division of labour. Section~\ref{sec:failures} predicts
which failures should move --- the $8$ malformed outputs and the $22$ wrong
return types are exactly the kind a more capable model fixes.

\paragraph{Why the DSL was frozen.} A composable, CLEVR-style catalogue of
typed operations \cite{clevr} --- \code{filter}, \code{unique}, \code{relate},
\code{same\_status}, \code{query}, with explicit input and output types --- is
implemented in the repository and deliberately \emph{not} wired into any
experiment. It would widen coverage from four families to the whole benchmark,
but Table~\ref{tab:triage} says the current failures are overwhelmingly not
expressiveness. Building a new language and changing model size at once would
leave neither attributable.

\paragraph{Why the distillation line was dropped.} The previous report proposed
distilling the fine-tuned LLM into a smaller student. Distillation reduces the
cost of a demonstrated capability; it cannot create one, and no spatial
competence was established in the teacher.

% =====================================================================
\section{Conclusion}
% =====================================================================

The original project established that the LiDAR-LLM architecture can be wired
up on a laptop, and nothing more. This revision asks a narrower question that
the same hardware answers: given one frozen $1.5$B model and one object list,
is it better to produce the answer or to produce a program? On held-out
nuScenes drives, the program. The margin is large, paired, and consistent
across all three drives, and the scene-dependence control shows the direct mode
largely reciting template answers while the executed mode tracks the scene.

The two findings most likely to be useful elsewhere are not about the
comparison. The six nuScenes-QA relations are uniform $60^{\circ}$ bearing
sectors, recovered by fitting the reference answers rather than assumed, and
the appealing six-camera reading is wrong. And $23\%$ of nuScenes annotations
have no LiDAR return at all while the benchmark counts them, so filtering
objects by LiDAR support --- the obvious thing to do when building from a point
cloud --- costs $49$ accuracy points on otherwise correct programs.
