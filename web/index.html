Answer it, or compute it?

The same small language model reads a driving scene as a list of objects. Asked to reply directly, it guesses. Asked to write a program instead, it lets an executor do the counting.

In short

LiDAR-LLM turns 3D scene understanding into text generation. This study holds perception fixed, using the ground-truth nuScenes objects, and asks a narrower question: given the objects, should a frozen language model produce the answer, or write a program that computes it?

On 200 held-out questions from three drives never seen during development, Qwen2.5-1.5B is right 50.5 % of the time when it answers directly and 68.5 % when its program is executed. Its counting error falls from 2.16 to 0.68.

The advantage holds up to 32B parameters, then one hosted model reaches parity. This is a controlled diagnostic with oracle perception, not a new detector or a benchmark record.

What the model is given

Each question in NuScenes-QA [2] is attached to one keyframe of a drive. Instead of raw points, both methods here receive the same object list: one row per annotated object with its category, its position in metres in the ego vehicle’s frame, and its status. Positions are rounded to 0.1 m for both.

That list is the entire scene as far as the model is concerned. Hover a row or a box to link them.

Directions are a convention

“To the front left of the bus” sounds obvious until you have to compute it. NuScenes-QA defines it in its Equation 2: six relations, each a 60° sector of bearing, measured from the reference object while keeping the ego vehicle’s heading. There is no standalone “left” or “right”.

An earlier version of this project used eight 45° sectors and quietly selected the wrong objects. The executor now has the convention written down in exactly one place, and the direct model is given the same definition in its prompt. Click an object to measure directions from it.

The sectors are half-open intervals (low, high], so an object exactly on a boundary belongs to one sector only. Objects closer than 1 m to the reference get no direction at all, because their bearing is unstable.

Writing a program instead

In the program mode the model never sees the scene. It reads only the question and writes one JSON object: an operation over a selector, a category with an optional status, direction and anchor. A deterministic executor then runs it on the object list.

The executor refuses rather than guesses. “The bus” presupposes exactly one bus; if there are three, the answer is ambiguous and counts as wrong. Build a program and run it on any keyframe. This is the same executor, ported to TypeScript and checked against every archived run.

Two hundred questions, two answers each

The evaluation set has 200 questions from three drives that were held out from all prompt development. Invalid programs and refusals count as wrong, so the program mode answers fewer questions (91 %) and still wins. Paired question by question, only the executed answer is right on 67 questions and only the direct one on 31.

The table holds every archived answer. Pick a model, click a cell of the grid to filter, click a question to see its scene.

Where the gain comes from

Counting is the clearest case. Asked how many objects match, the direct model is off by 2.16 objects on average, and 1.84 of that comes from undercounting. It tends to say “1”. The executor counts, and is off by 0.68.

The other gain is subtler. NuScenes-QA repeats some questions word for word across keyframes, with different correct answers. A system that ignores the scene can’t follow. In the 13 such groups, the executed answer is right in every scene of all 13; the direct answer manages that in 1, and gives the same answer to every scene in 4.

Does scale close the gap?

Partly. The same comparison was archived for five more models. Larger Qwen2.5 checkpoints write valid programs more often, and the executed mode keeps its lead up to 32B. One hosted endpoint, qwen3.8-27b, answers directly almost as well as its programs do.

That last row is a counterexample to any claim of a universal execution advantage. It is not evidence that “reasoning” rather than size explains the change: too many factors moved at once.

A wider test goes the other way. On 280 broader questions, a typed CLEVR-style language raises what the program can express from 27.5 % to 98.5 % of the benchmark, yet at 1.5B its accuracy drops to 29.6 %, below the direct answer at 52.1 %. Its programs are right 85.6 % of the time when they run, but they run on only 34.6 % of questions.

A data check worth knowing

In the processed mini annotations, 4,278 of 18,538 objects have zero LiDAR returns: the annotator placed a box, but the sensor saw nothing there. NuScenes-QA still counts them. Keeping only objects that LiDAR actually hit drops the executor’s exact accuracy from 0.824 to 0.336 on 125 paired counting questions.

So a perfect detector working from the point cloud would be scored as wrong on many of these questions. This is a mismatch between labels and input on that subset, not a global detector score. Switch Figure 1 to LiDAR returns to see hollow boxes the sensor missed.

What this does not show

  • Perception is an oracle. Object lists and statuses are ground-truth annotations. No detector was run, so nothing here measures LiDAR perception.
  • Three drives are not a population. The gain is positive on each evaluation drive (+21.2, +18.8 and +13.8 points), but questions within a drive are correlated. The sign test is descriptive.
  • The narrow comparison covers selected question families. The full benchmark subset has 5,916 questions; the frozen manifest keeps 100 development and 200 evaluation questions.
  • Program execution is not new. CLEVR and Neural-Symbolic VQA did it years ago. The contribution is an auditable, same-checkpoint comparison on driving questions, with scene-disjoint splits and failure traces.
  • The larger runs used different hardware. The core 1.5B comparison ran on a T4; the hosted rows record provider aliases, not immutable checkpoints.

Check it yourself

Every saved number can be recomputed without a GPU. The audit re-derives correctness and every summary field from the 1,580 per-question records of eight comparisons, checks manifest membership and scene separation, and fails on any disagreement.
