Answer it, or compute it?

A small language model reads a driving scene as a list of objects. Ask it to reply directly and it guesses. Ask it for a program and an executor does the counting.

In short

LiDAR-LLM turns 3D scene understanding into text generation. This study holds perception fixed by using the ground-truth nuScenes objects, and asks something narrower. Once the objects are known, should a frozen language model produce the answer, or write a program that computes it?

On 200 held-out questions from three drives never seen during development, Qwen2.5-1.5B is right 50.5 % of the time when it answers directly and 68.5 % when its program is executed. Its counting error falls from 2.16 to 0.68.

The advantage holds up to 32B parameters. Past that, one hosted model reaches parity. Keep in mind that this is a controlled diagnostic with oracle perception. There is no new detector here and no benchmark record.

What the model is given

Each question in NuScenes-QA [2] is attached to one keyframe of a drive. Neither method sees raw points. Both get the same object list, with one row per annotated object giving its category, its position in metres in the ego vehicle’s frame, and its status. Positions are rounded to 0.1 m in both cases.

As far as the model is concerned, that list is the whole scene. Hover a row or a box to see which goes with which.

Directions are a convention

“To the front left of the bus” sounds obvious until you have to compute it. NuScenes-QA pins it down in its Equation 2. There are six relations, each a 60° sector of bearing, measured from the reference object but using the ego vehicle’s heading. A plain “left” or “right” does not exist.

My earlier version of this project used eight 45° sectors and quietly selected the wrong objects. Now the convention lives in exactly one place in the executor, and the direct model gets the same definition in its prompt. Click an object to measure directions from it.

The sectors are half-open intervals (low, high], so an object exactly on a boundary belongs to one sector only. Objects closer than 1 m to the reference get no direction, since their bearing is unstable.

Writing a program instead

In program mode the model never sees the scene. It reads the question and writes one JSON object: an operation over a selector, which is a category with an optional status, direction and anchor. A deterministic executor then runs that on the object list.

When in doubt, the executor refuses. “The bus” presupposes exactly one bus, so if there are three the answer is ambiguous, which counts as wrong. You can build a program below and run it on any keyframe. It is the same executor, ported to TypeScript and checked against every archived run.

Two hundred questions, two answers each

The evaluation set has 200 questions from three drives that were kept out of all prompt development. Invalid programs and refusals count as wrong. The program mode answers fewer questions (91 %) and wins anyway. Paired question by question, only the executed answer is right on 67 questions and only the direct one on 31.

Where the gain comes from

Counting shows it most clearly. Asked how many objects match, the direct model is off by 2.16 objects on average, and 1.84 of that is undercounting. It likes to say “1”. The executor actually counts, and is off by 0.68.

The second gain is less obvious. NuScenes-QA repeats some questions word for word across keyframes, with different correct answers, and a system that ignores the scene can’t keep up. There are 13 such groups. The executed answer is right in every scene for all 13. The direct answer manages that for 1, and in 4 it gives the same answer to every scene.

Does scale close the gap?

Partly. I archived the same comparison for five more models. Larger Qwen2.5 checkpoints write valid programs more often, and the executed mode stays ahead up to 32B. One hosted endpoint, qwen3.8-27b, answers directly almost as well as its programs do.

That last row is a counterexample to any claim of a universal execution advantage. But it doesn’t show that “reasoning” rather than size explains the change. Too many factors moved at once.

A wider test points the other way. On 280 broader questions, a typed CLEVR-style language lets programs express 98.5 % of the benchmark instead of 27.5 %. At 1.5B, though, accuracy drops to 29.6 %, below the direct answer at 52.1 %. When its programs run they are right 85.6 % of the time, but they run on only 34.6 % of questions.

A problem in the labels

In the processed mini annotations, 4,278 of 18,538 objects have zero LiDAR returns. Someone drew a box, but the sensor saw nothing there. NuScenes-QA still counts them. If I keep only the objects LiDAR actually hit, the executor’s exact accuracy on 125 paired counting questions drops from 0.824 to 0.336.

A perfect detector working from the point cloud would therefore be marked wrong on many of these questions. What this measures is a mismatch between labels and input on that subset. It is not a global detector score. Switch Figure 1 to LiDAR returns to see hollow boxes the sensor missed.

What this does not show

  • Perception is an oracle. Object lists and statuses are ground-truth annotations, and since no detector was run, nothing here measures LiDAR perception.
  • Three drives are not a population. The gain is positive on each evaluation drive (+21.2, +18.8 and +13.8 points), but questions within a drive are correlated, so the sign test is only descriptive.
  • The narrow comparison covers selected question families only. Of the 5,916 questions in the full benchmark subset, the frozen manifest keeps 100 for development and 200 for evaluation.
  • Program execution is not new; CLEVR and Neural-Symbolic VQA did it years ago. What this study adds is an auditable, same-checkpoint comparison on driving questions, with scene-disjoint splits and failure traces.
  • The larger runs used different hardware. The core 1.5B comparison ran on a T4, and the hosted rows record provider aliases rather than immutable checkpoints.

Check it yourself

You can recompute every saved number without a GPU. The audit re-derives correctness and every summary field from the 1,580 per-question records of eight comparisons. It also checks manifest membership and scene separation, and fails on any disagreement.
