Answer it, or compute it?

A small language model reads a driving scene as a list of objects. Ask it to reply directly and it guesses. Ask it for a program and an executor does the counting.

In short

The released NuScenes-QA answers do not tell left from right. The benchmark’s six spatial relations are published as signed 60° sectors. Its answers follow the unsigned angle to the ego heading instead: “front left” holds on either side, so does “back right”, and “front right” and “back left” never hold. In the official train and validation sets, all 12,392 counting or existence questions about those two relations are answered 0 or no. Two more conventions sit beside this one: “things” are every annotation plus the ego vehicle, and objects with no LiDAR return are counted. I inferred these rules from the answers and did not read the benchmark’s generation code.

The study itself holds perception fixed, using the ground-truth nuScenes objects, and asks something narrow. Once the objects are known, should a frozen language model produce the answer, or write a program that an executor computes? My archived comparison told both modes the published convention. With the convention the answers follow, on 200 questions from three drives, Qwen2.5-1.5B is right 54.0 % of the time when it answers directly and 76.5 % when its program is executed (50.5 % and 68.5 % as published). For Qwen2.5-7B it is 54.5 % against 95.0 %. The share of these questions that at least one of six models’ programs gets right moves from 86 % to 98 %.

On 1,460 questions from 146 validation drives that no prompt was developed on, the 7B model’s programs are ahead of its direct answers by +36.6 points [+33.7, +39.5], a 95 % interval over drives. This remains a controlled diagnostic with oracle perception on a few question families. Asking the 1.5B and 7B models to reason before answering did not close the gap, which says nothing general about whether language models can reason spatially.

What the model is given

Each question in NuScenes-QA [2] is attached to one keyframe of a drive. Neither method sees raw points. Both get the same object list, with one row per annotated object giving its category, its position in metres in the ego vehicle’s frame, and its status. Positions are rounded to 0.1 m in both cases.

As far as the model is concerned, that list is the whole scene. Hover a row or a box to see which goes with which.

The answers do not tell left from right

“To the front left of the bus” sounds obvious until you have to compute it. NuScenes-QA pins it down in its Equation 2. There are six relations, each a 60° sector of bearing, measured from the reference object but using the ego vehicle’s heading. A plain “left” or “right” does not exist. Read as written, the sectors are signed: front left runs from 30° to 90° counter-clockwise of straight ahead, and front right is its mirror image. My archived runs used that reading, and both modes were told it.

The released answers follow another rule. Take a, the unsigned angle between the ego heading and the direction to the object, from 0° to 180°. “Front” is a ≤ 30°. “Front left” is 30° < a ≤ 90°, on either side. “Back right” is 90° < a ≤ 150°, on either side. “Back” is a > 150°. “Front right” and “back left” are never true. This is what the arccos of a normalised dot product gives when the sign of the angle is never recovered. Figure 2 draws both readings; click an object to measure directions from it.

Under both readings the intervals are half-open (low, high], so an object exactly on a boundary belongs to one relation only. Objects closer than 1 m to the reference get no direction, since their bearing is unstable.

The evidence needs no geometry

Take every counting or existence question of the official release that names exactly one relation, and count how often the answer is 0 or no. For four of the relations that happens between 20.2 % and 23.9 % of the time. For “front right” and “back left” it happens every time: 12,392 questions over 34,117 keyframes, and not one of them has an object there. The same holds on v1.0-mini (37 of 37 and 41 of 41).

Checked on data that did not suggest the rule

I read the rule off evaluation failures of my first comparison, so it has to be tested elsewhere. On the development split, with reference programs verified by hand, the executor reproduces 91 of 100 answers under the signed sectors and 99 under the unsigned rule; the one left over is a question whose reference object is not unique. The same procedure on the evaluation split gives 195 of 200. On the official validation set, a rule parser answers 25,973 questions and agreement goes from 82.8 % to 91.9 %, with the whole change on the four diagonal relations. That parser was not verified by hand and its own programs are sometimes wrong, so the last figure is a floor on agreement and not a measure of label noise.

“Things” include the ego vehicle

For “How many things are there?”, the answer equals the number of annotations of the keyframe, of every category, plus one. That holds for all 2,728 such questions in the official release (2,080 in train, 648 in validation). Counting only the ten classes the questions name, plus one, matches 1,610 and 495 of them. So a “thing” includes classes no question ever names, such as pushable objects, debris, bicycle racks and animals. It includes boxes with no LiDAR return. And it includes the ego vehicle, which also counts in relations between objects, though never to the front or back “of me”. I found this on the validation drives and confirmed it on train, which I had not looked at before.

With both rules applied, the executor agrees with reference programs on 97.5 % of 1,460 questions from 146 validation drives, against 85.1 % under the published reading. The object list of Figure 1 and every archived run use the ten named classes; on v1.0-mini that changes one question in 300.

Objects the sensor did not see are counted

In the v1.0-mini annotations, 4,278 of 18,538 objects have zero LiDAR returns. Someone drew a box, but the sensor saw nothing there. The answers count them. Hold the programs fixed and change only the object list: on the 249 counting questions of v1.0-mini that both conditions answer, exact accuracy falls from 94.0 % with every annotation to 44.2 % with only the objects LiDAR hit. On the official validation set (10,087 questions) it falls from 82.7 % to 42.0 %. Under the signed sectors the same drop is 79.9 % to 37.3 % and 72.5 % to 37.0 %.

A perfect detector working from the point cloud would therefore be marked wrong on many of these questions. This measures a mismatch between labels and input on that subset. It is not a detector score. Switch Figure 1 to LiDAR returns to see hollow boxes the sensor missed.

What this means if you use the benchmark

  • A model can score well on the directional questions with no notion of left and right, and a model that has one is penalised: a correct count of the cars to the front right is marked wrong whenever there is one.
  • A LiDAR-only system is asked to count objects its sensor did not return, and objects of classes its detector does not have.
  • Results reported on NuScenes-QA stay comparable with each other, since every system faces the same labels. What changes is what a number means. It measures agreement with these conventions, not left/right spatial reasoning.
  • The rules are descriptions of the released labels. Reading the generation code could confirm or refine them. Some questions still disagree under all three: 36 of 1,460 on the validation drives, which I did not investigate further.

Writing a program instead

In program mode the model never sees the scene. It reads the question and writes one JSON object: an operation over a selector, which is a category with an optional status, direction and anchor. A deterministic executor then runs that on the object list.

A program names a relation, such as front_left. What that relation selects is the executor’s convention, kept in exactly one place. So when the convention turns out to be wrong, the saved programs can be executed again under the right one, with no GPU and no new generation. The direct mode has no such separation: its prompt states the convention, and correcting it needs a new run.

When in doubt, the executor refuses. “The bus” presupposes exactly one bus, so if there are three the answer is ambiguous, which counts as wrong. You can build a program below and run it on any keyframe under either convention. It is the same executor, ported to TypeScript and checked against the Python execution of every archived program under both.

Two hundred questions, two conventions

The first comparison has 200 questions from three drives that were kept out of all prompt development. Invalid programs, refusals and unreadable answers count as wrong. As archived, both modes worked under the published convention: the direct prompt, direct-1, stated the signed sectors and the executor applied them. Qwen2.5-1.5B was then right 50.5 % of the time directly and 68.5 % through its program.

Correcting the two modes takes different work. The programs are executed again under the rule the answers follow and reach 76.5 %. The direct mode gets a new run with a new prompt, direct-2, which states that rule, and reaches 54.0 %. Paired question by question, only the executed answer is right on 71 questions and only the direct one on 26 (67 and 31 as published). The program mode answers fewer questions (91 %) and wins anyway.

Every archived answer is in the table below. Pick a model, switch the convention, and click a cell of the grid to filter. Clicking a question shows its scene, what the executor selects, and the program’s answer under both conventions. For the three hosted models the direct mode was not rerun, so their direct column stays the direct-1 answer.

Direct or program, once the convention is right

The same re-execution applies to all six archived models, and program accuracy rises for each of them. Under the published layout, 28 of the 200 questions were wrong in program mode for all six, so none of these programs could pass 86 %. 27 of them ask about a direction, where the executor applied a rule the answers do not follow. Executed as labelled, 4 remain and that bound is 98 %. For the 32B model, correct answers go from 15 to 25 of 27 on “front left” questions, 5 to 11 of 11 on “front right”, 10 to 16 of 16 on “back left” and 12 to 17 of 18 on “back right”.

The direct mode gains less from being told the right rule: from 50.5 % to 54.0 % at 1.5B, 50.5 % to 54.5 % at 7B, and 58.0 % to 64.0 % at 32B.

A bare answer in a few tokens may be an unfair format, so I also asked for the working first and read a final Answer: line, with a 2,048-token budget chosen on the development split. For the 1.5B model this hurts. Under direct-2r it is right 34.5 % of the time, and 56 of its 200 outputs contain no readable answer, which counts as wrong. For the 7B model it helps, from 54.5 % to 62.5 %, at 427 output tokens per question. That is still far below its programs at 95.0 %.

Constrained decoding is a separate condition, because it changes the decoder and not only the prompt. Programs are decoded under a JSON Schema whose categories, statuses, relations and operations are closed sets. Invalid programs go from 8 to 0 at 1.5B and from 1 to 0 at 7B, and accuracy moves from 76.5 % to 80.5 % and from 95.0 % to 95.5 %.

On 146 held-out drives

Three drives are a thin basis. A second manifest takes 1,460 questions from 146 drives of the official validation set, none of them in v1.0-mini and none used to write a prompt or to find the left/right rule. The “things” rule was found on them. Each model answers them twice in both modes. Once under the published conventions: signed sectors, the ten named classes, direct-1. Once as labelled: the unsigned angle, every annotation and the ego vehicle as things, direct-2. Questions within a drive share its vehicles and its road, so the intervals resample drives, not questions.

As labelled, the 7B model is right 59.5 % of the time directly and 96.1 % through its programs, a difference of +36.6 points [+33.7, +39.5]. Its programs are ahead on 143 drives and behind on 0. For the 1.5B model the difference is +16.6 points [+12.5, +20.5], ahead on 108 drives and behind on 29. The advantage was already there under the published conventions (+27.1 points [+24.4, +29.8] and +15.8 points [+12.2, +19.2]).

It is not uniform. On questions that measure a direction from another object, the 1.5B model’s programs are right 33.1 % of the time and its direct answers 47.9 %. The 7B model shows no such reversal: there it is 92.1 % against 39.3 %.

Where the gain comes from

Counting shows it most clearly. Asked how many objects match, the 1.5B model answering directly under direct-2 is off by 2.42 objects on average, and 2.20 of that is undercounting. It likes to say “1”. The executor actually counts, and is off by 0.34. As published the two errors were 2.16 and 0.68.

The second gain is less obvious. NuScenes-QA repeats some questions word for word across keyframes, with different correct answers, and a system that ignores the scene can’t keep up. There are 13 such groups. The executed answer is right in every scene for 13 of them. The direct answer manages that for 1, and in 2 it gives the same answer to every scene.

Does scale close the gap?

Not among the models I could rerun. Larger Qwen2.5 checkpoints write valid programs more often, and from 1.5B to 32B the executed mode stays well ahead under either convention (Figure 7). One hosted endpoint, qwen3.8-27b, is the exception in the archive. Told the published convention, it answered directly 84.0 % of the time, level with its programs under that convention at 84.5 %. That is a counterexample to any claim of a universal execution advantage. Its programs reach 98.0 % when executed as labelled, but its direct mode was not rerun under direct-2, so the corrected comparison for this model is open. Nor does the row show that “reasoning” rather than size explains the change. Too many factors moved at once.

A cleaner probe holds the weights fixed. Qwen3-8B has a thinking switch in its chat template. With thinking off, on the first comparison as labelled, it is right 58.0 % of the time directly and 98.0 % through its programs. With thinking on, under a 4,096-token budget fixed in advance, the same weights reach … directly and … through programs.

A wider test points the other way. On 280 broader questions, a typed CLEVR-style language lets programs express far more of the benchmark. At 1.5B, though, its accuracy is 29.6 % under the published layout and 31.4 % as labelled, below the direct-1 answer at 52.1 %. When its programs run they are right 85.6 % of the time under the published layout, but they run on only 34.6 % of questions.

What this does not show

  • Perception is an oracle. Object lists and statuses are ground-truth annotations, and since no detector was run, nothing here measures LiDAR perception.
  • It does not show that language models cannot reason spatially. Asking for the working did not close the gap for the 1.5B and 7B models, with one prompt wording and one token budget. That is all the ablation says.
  • The comparison covers four question families: counting or existence, with a status, with a direction from the ego vehicle, and with a direction from another object. The wider test above is a single model.
  • The first comparison rests on three evaluation drives. The gain is positive on each (+24.6, +21.2, +21.7 points as labelled, +21.2, +18.8, +13.8 as published), but three drives are not a population. The interval over 146 validation drives is the one to rely on, and it exists only for the models in Figure 9.
  • The label rules are inferred from the answers. I did not read the benchmark’s generation code.
  • All prompts were developed on v1.0-mini, including direct-2, the wording of the reasoned prompt and its token budget. The validation drives are new drives of the same benchmark and the same four families, and the “things” rule was found on them.
  • The 32B model is 4-bit quantised. The hosted rows record provider aliases rather than immutable checkpoints, and the direct mode of the hosted Qwen3 models was not rerun under the corrected prompt.
  • The runs used different hardware: a T4 for the 1.5B model, an A10G for the 7B, an L40S for the 32B.
  • Program execution is not new; CLEVR and Neural-Symbolic VQA did it years ago. What this study adds is an auditable, same-checkpoint comparison on driving questions, with scene-disjoint splits and failure traces, and an account of what the labels encode.

Check it yourself

You can recompute every saved number without a GPU and without downloading nuScenes. The audit re-derives correctness and every summary field from the per-question records of the eight archived comparisons and of their eight re-executed counterparts. It also checks manifest membership and scene separation, and fails on any disagreement. The next two commands rebuild the tables of the November 2026 runs and a drive-level interval from the saved rows.

python -m pip install -r requirements-audit.txt
python -m spatial_reasoning.audit_results
python -m spatial_reasoning.summarise_runs
python -m spatial_reasoning.drive_bootstrap spatial_reasoning/results/runs_2026_11/val_new_7b/rows_eval.jsonl \
  --against spatial_reasoning/results/runs_2026_11/val_old_7b/rows_eval.jsonl

The label audit and the re-execution need the official questions and the nuScenes metadata, without sensor data; reproduction.md says where to get them.

# left and right without geometry, and what a "thing" is
python -m spatial_reasoning.audit_labels \
  --questions data/data/nuscenes_qa/NuScenes_train_questions.json data/data/nuscenes_qa/NuScenes_val_questions.json \
  --metadata-root data/data/nuscenes/v1.0-trainval --out outputs/label_audit.json
# the executor against hand-verified reference programs, under each reading
python -m spatial_reasoning.verify_executor --manifest spatial_reasoning/manifests/first_comparison.json \
  --metadata-root data/data/nuscenes/v1.0-mini --split dev --layout nuscenes_qa_as_labelled --out outputs/ev_as_labelled
# every archived program executed again as labelled
python -m spatial_reasoning.rescore_programs --metadata-root data/data/nuscenes/v1.0-mini --out outputs/rescored_as_labelled
python -m spatial_reasoning.analyse_rescored --rescored outputs/rescored_as_labelled
